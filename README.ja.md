# claude-memory-bookstore

[English](README.md) · [简体中文](README.zh-CN.md) · [繁體中文](README.zh-TW.md) · [한국어](README.ko.md) · **日本語**

[Claude Code](https://claude.com/claude-code) のための永続メモリシステムです。数百ファイル・数百万文字まで拡張できますが、セッションごとに自動でコンテキストに読み込まれるのはごくわずかな一部だけです。

数十件の長期プロジェクトにまたがって、もう数か月間このシステムを運用しています。前回確認した時点では:**保存されている文字数は250万文字、そのうち毎回のセッションで自動的に読み込まれるのはわずか0.8%**でした。これはバグではなく、設計そのものです。

**6週間後に測り直しました:921ファイルで644万文字、そして自動読み込みされるインデックスは0.26%まで下がっていました。** 保管量は2.6倍になり、常時かかるコンテキストのコストは3分の1になりました。この6週間で何を変えたかは後ろの章に書いてあります。悪化した比率も含めて。

## このシステムが解決する課題

Claude Code のセッションにはコンテキストウィンドウの上限がありますが、メモリストアには上限がありません。AIアシスタントに「すべてを覚えさせよう」として毎回全履歴を渡してしまうと、逆効果になります。的外れな部分を読み、重要な箇所を見落とし、メモリシステムなしより遅くなってしまいます。

本当の解決策は、より多く検索することではなく、デフォルトで読み込む量を減らし、「何を覚えるか」ではなく「どこを探せばよいか」をシステムに教えることです。

## アーキテクチャ:3層構造

```
第1層 — インデックス(常に読み込み)      全体の0.26%、読み込み頻度100%
第2層 — トリガー & ルール(必要時)       全体の13%、grepでヒットした時のみ読み込み
第3層 — 一次情報源(必要時)             全体の87%、開いた時のみ読み込み
```

**第1層 — `MEMORY.md`。** 1つの記憶につき1行:「ファイルが存在する + 一言のフック」。知識そのものではなく、*どこに知識があるか*を保存します。Claude Code が新しいセッションのたびに自動で読み込む唯一のファイルです。

**第2層 — トリガーテーブル + ルール。** キーワード(「トリガー」——何かを思い出そうとする時に自然に入力する言葉)を一次情報源ファイルにマッピングする、手作業で維持する転置インデックスです。このファイルは肥大化しやすく(自分の実物は10万文字を超えています)、そのため「まず `grep`、それから該当行範囲だけを読む」という規律を課しています。全文を一度に読むと静かに切り詰められ、気づかないまま後半を失ってしまいます。

**第3層 — 一次情報源。** プロジェクト/トピックごとに1ファイル、引き継ぎごとに1ログ、重要な意思決定ごとに1つの決定記録。すべての結論はここにあります。上の2層はこの層の投影にすぎず、第3層と食い違えば常に第3層が優先されます。

## 読み取りパス:キーワード1つが知識にたどり着くまで

1. 任意のセッションでトリガーワードを入力します——プロジェクトのコード名、インシデント名、自然に思い浮かぶ言葉なら何でも構いません。
2. Claude がトリガーテーブルをそれで `grep` します(全文読み込みではなく、上記の第2層の方式)。
3. ポインタと一言の現状を受け取ります:`状態 トリガーA · トリガーB → 一次情報源ファイル [確定事実]`。角括弧の中には、grep がヒットしたその瞬間に必要なものだけが入ります——ロールバック手順、確定した数値、結論。
4. 一次情報源ファイルを開き、そこから作業を続けます。インデックスにキャッシュされた判断には権威がありません——最終的な根拠は一次情報源ファイルの内容だけです。

## 書き込みパス:3段階の自動ゲート

**ゲート0 — バックアップ + バージョン管理層**(`hooks/memory_backup.sh`、すべての `PostToolUse` の `Write|Edit` で実行):メモリディレクトリをバックアップ先にミラーリングし、書き込みのたびに git にコミットします。バックアップドライブがマウントされていない場合は静かに失敗し、重複を排除したアラートを1回だけ送信します(無限にリトライしません)——ドライブが復旧すれば次の書き込みで自動的に追いつきます。

**ゲート1 — ストックゲート**(`hooks/memory_size_gate.py`):インデックスのサイズが閾値を超えた時、あるいはトリガーテーブルが1日で大きく肥大化した時に、任意の通知チャンネル経由で警告します。3つの判定基準があり、それぞれ1日1回までしか発火しないため、無視するようになるノイズにはなりません。

**ゲート2 — フローゲート**(同じスクリプト内の新しい部分):ストックゲートだけでは不十分でした。インデックス増加の内訳を分解したところ、**新規追加行と既存行の肥大化の比率がおよそ4~7:1**であることが判明しました——つまり定期的な整理は常に対症療法にすぎず、翌日には同じ症状が再発するということです。フローゲートは代わりに、書き込みのまさにその瞬間に問題を捕まえます。今インデックスに追加した差分を検査し、新しい行が長すぎる、同じ一次情報源が2つの行から重複して参照されている、あるいは古いイベントポインタを引退させずに新しいものを追加した、といった場合には、そのフィードバックを**まさに今書き込んだ同じ Claude セッション**に返します——`PostToolUse` フックの `hookSpecificOutput.additionalContext` フィールド経由であり、`exit 2` ではありません(こちらは人間にしか表示されず、モデルのコンテキストには届きません)。

## 記憶が矛盾した時、何が優先されるか

2つの記憶が食い違う場合、優先順位は:その場でのあなたの明示的な指示(常に最優先)> 一次情報源ファイル > トリガーテーブルの投影 > インデックスのフック行 > 古いログのスナップショット。同じ階層同士の矛盾は、より新しい日付が優先されます。それでも解決できない場合、システムは勝手に折衷案を出さず、あなたに尋ねます。

## この6週間で変わったこと

3層構造そのものは持ちこたえました。最初のコミット以降に追加したもの:

**アーカイブ層**(`_archive_index.md`)。終わったプロジェクトや動きの止まった案件は削除せず、降格させます:インデックスの行だけを別ファイルへ移し、一次情報源のファイルはその場に残します。削除すると「それはもう試した」という答えが失われます。自分が一番よく引くのはその答えです。

**インデックスの分割。** インデックス自体にも上限がありました。あるプロジェクトがインデックス内で66行まで膨らみ、ファイル全体の3分の2を占めていました。毎日触る案件ではありません。その66行を `_matrix_index.md` に切り出し、メインのインデックスには1行だけポインタを残しました。

**「出来事ごと」から「プロジェクトごと」へ。** インデックスは当初、出来事1件につき1行を延々と追記していく台帳でした。プロジェクト単位に整理し直した(プロジェクトごとにアーカイブファイルを1つ作り、新しい出来事はインデックスではなくその中に追記する)結果、インデックスは24,349文字から20,760文字に減り、失われた情報はありません。

**体積は文字数で測る。バイト数では測らない。** `wc -c` はインデックスの体積を3回誤診し、そこでようやく気づきました。CJK文字は1文字3バイトなので、バイト数では3倍に見えます。サイズゲートの閾値はすべて `len(open(path, encoding='utf-8').read())` を使うようにしました。

### 第2層のコスト

第2層は比率を保てませんでした。トリガーテーブルは現在、全体の13%を占めています。上に書いた約6%から倍以上で、1ファイルで849,747文字あります。

そのうち半分近くは意図的に残しているものです。400,240文字(47%)が「アーカイブ / 沈殿済み」の見出しの下にあり、終わったプロジェクト、取りやめた案件、置き換えられた案件が入っています。それらのトリガー語はインデックスに残したままです。このシステムでトリガー語を退役させるとは、削除ではなくブックマークへの降格を意味します。数か月後でも人は古いコードネームを打つからです。そしてその時こそ「それはもう終わった、今は X を見ろ」と答えてほしい場面です。

つまりこの増加は、その選択の既知のコストです。フローゲートが今も取りこぼすのは残り半分のほうです。その行は存在して当然で、しかも毎月さらに伸び続けている。トリガー語のヒットデータを持っていないので、支えになっている行と単に古いだけの行を区別できません。

この規模でも「先にgrep、それから読む」という規律は機能しています。

## セットアップ

1. `hooks/memory_backup.sh` と `hooks/memory_size_gate.py` を `~/.claude/hooks/` にコピーし、各ファイル冒頭のプレースホルダーパス(バックアップ先、通知用の env ファイル、メモリディレクトリ)を自分の環境に合わせて書き換えます。
2. バックアップフックを `~/.claude/settings.json` に接続します:

```json
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Write|Edit",
        "hooks": [
          {
            "type": "command",
            "command": "jq -r '.tool_input.file_path // empty' | /bin/bash $HOME/.claude/hooks/memory_backup.sh",
            "timeout": 120,
            "async": true
          }
        ]
      }
    ]
  }
}
```

3. 自分用のメモリディレクトリを作成し(ファイル構成は `demo/` を参照)、`MEMORY.md` に1行のフックとしてエントリを書き始めます。具体的な詳細はその隣にある各トピックファイルに置きます。
4. バックアップ/サイズゲートに Telegram 通知を接続したい場合は、`TG_TOKEN` / `TG_CHAT_ID` を env ファイルに入れ、`TG_ENV` にそのファイルを指定してください——このファイルは絶対にコミットしないでください(`.gitignore` に既に含まれています)。

## `demo/` の中身

想定されるフォーマットを示す、完全に架空のサンプルファイル群です(架空の「ウィジェットローンチ」プロジェクト)——`MEMORY.md` のインデックスエントリ、トリガーテーブルの抜粋、一次情報源のトピックファイル1件。このリポジトリには実際のプロジェクト・顧客・アカウント情報は一切含まれていません。README 内の数値(644万文字、0.26%、3層構造)は自分自身の実際の利用状況から取ったものですが、閲覧できるファイルの中身はすべてプレースホルダーです。
