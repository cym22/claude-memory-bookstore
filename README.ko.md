# claude-memory-bookstore

[English](README.md) · [简体中文](README.zh-CN.md) · [繁體中文](README.zh-TW.md) · **한국어** · [日本語](README.ja.md)

[Claude Code](https://claude.com/claude-code)를 위한 영구 메모리 시스템입니다. 수백 개의 파일과 수백만 자까지 확장되지만, 세션마다 자동으로 컨텍스트에 로드되는 양은 아주 작은 조각뿐입니다.

몇 달째 수십 개의 장기 프로젝트에 걸쳐 이 시스템을 운영하고 있습니다. 마지막으로 확인했을 때: **250만 자가 저장되어 있고, 세션마다 자동으로 읽히는 건 그중 0.8%뿐**이었습니다. 이것이 설계 자체이고, 설계상의 버그가 아닙니다.

**6주 뒤에 다시 측정했습니다: markdown 파일 921개에 644만 자, 자동으로 로드되는 인덱스는 0.26%입니다.** 같은 기준으로 재면 저장량은 약 2.3배가 되었습니다(위의 250만은 반올림한 숫자이고, 첫 커밋 당일 실측은 281만이었습니다). 인덱스 자체는 1.88만 자에서 1.68만 자로 줄었으니, 비율이 내려간 주된 이유는 분모가 커졌기 때문입니다. 이 6주 동안 무엇을 바꿨는지는 뒤쪽 장에 적어두었습니다. 나빠진 비율까지 포함해서.

## 이 시스템이 해결하는 문제

Claude Code 세션의 컨텍스트 창은 한정되어 있지만, 메모리 저장소에는 한계가 없습니다. AI 어시스턴트가 "모든 걸 기억하게" 하려고 매번 전체 히스토리를 다 넣어주면 정반대의 결과가 나옵니다. 엉뚱한 부분을 읽고, 중요한 내용을 놓치고, 메모리 시스템이 없을 때보다 오히려 느려집니다.

해결책은 더 많이 검색하는 게 아니라, 기본적으로 더 적게 로드하고 "무엇을 외울지"가 아니라 "어디를 찾아봐야 할지"를 시스템에게 가르치는 것입니다.

## 아키텍처: 3계층 구조

```
1계층 — 인덱스(항상 로드)         전체 용량의 0.26%, 로드 빈도 100%
2계층 — 트리거 & 규칙(필요 시)     전체 용량의 13%, grep으로 조회될 때만 로드
3계층 — 원본 소스(필요 시)        전체 용량의 87%, 열람될 때만 로드
```

**1계층 — `MEMORY.md`.** 메모리 하나당 한 줄: "파일이 존재한다 + 한 줄짜리 훅(hook)". 지식 자체를 저장하는 게 아니라 *지식을 어디서 찾을지*를 저장합니다. Claude Code가 새 세션마다 자동으로 읽어들이는 유일한 파일입니다.

**2계층 — 트리거 테이블 + 규칙.** 키워드("트리거" — 뭔가를 떠올리려 할 때 자연스럽게 입력하게 되는 문구)를 원본 소스 파일로 매핑하는, 손으로 관리하는 역색인입니다. 이 파일은 점점 커집니다(제 실제 파일은 약 85만 자를 넘습니다). 그래서 원칙은 이렇습니다: 먼저 `grep`으로 찾고, 그 다음 해당 줄 범위만 읽는다. 전체를 한 번에 읽으면 조용히 잘려나가고, 눈치채지 못한 채 뒷부분을 잃게 됩니다.

**3계층 — 원본 소스.** 프로젝트/주제마다 파일 하나, 인수인계마다 로그 하나, 중요한 결정마다 결정 기록 하나. 모든 결론은 여기에 있습니다. 위 두 계층은 이 계층의 투영일 뿐이며, 3계층과 충돌하면 항상 3계층이 우선합니다.

## 읽기 경로: 키워드 하나가 지식을 찾아가는 과정

1. 어느 세션에서든 트리거 단어를 입력합니다 — 프로젝트 코드명, 사건 이름, 자연스럽게 떠올리게 되는 아무 문구나.
2. Claude가 트리거 테이블에서 이를 grep으로 찾습니다(전체를 읽는 게 아니라 위 2계층 방식대로).
3. 포인터와 한 줄짜리 현황을 받습니다: `상태 트리거A · 트리거B → 원본소스파일 [핵심 사실]`. 대괄호 안에는 grep이 명중한 그 순간에 바로 필요한 것만 담습니다 — 롤백 명령, 핵심 수치, 결론.
4. 원본 소스 파일을 열어 거기서부터 작업합니다. 인덱스에 캐시된 판단은 권위가 없습니다 — 오직 원본 소스 파일의 내용만 최종 근거입니다.

## 쓰기 경로: 세 단계의 자동 게이트

**게이트 0 — 백업 + 버전 계층** (`hooks/memory_backup.sh`, 모든 `PostToolUse`의 `Write|Edit`에서 실행): 메모리 디렉토리를 백업 위치로 미러링하고, 쓸 때마다 git에 커밋합니다. 백업 드라이브가 마운트되어 있지 않으면 조용히 실패하고 중복 제거된 알림을 딱 한 번만 보냅니다(끊임없이 재시도하지 않음) — 드라이브가 다시 연결되면 다음 쓰기 때 자동으로 따라잡습니다.

**게이트 1 — 스톡 게이트** (`hooks/memory_size_gate.py`): 인덱스 크기가 임계값을 넘거나 트리거 테이블이 하루 만에 너무 많이 커지면, 여러분이 연결한 알림 채널로 경고합니다. 세 가지 판단 기준이 있고, 각각 하루에 최대 한 번만 발동해서 무시하게 되는 소음이 되지 않도록 합니다.

**게이트 2 — 플로우 게이트** (같은 스크립트에 추가된 부분): 스톡 게이트만으로는 부족했습니다. 인덱스 증가량을 성분 분석해보니 **새로 추가된 줄 대 기존 줄이 길어지는 비율이 대략 4~7:1**이었습니다 — 즉 주기적인 정리는 항상 증상만 고치고, 다음 날 다시 재발한다는 뜻입니다. 플로우 게이트는 대신 쓰는 바로 그 순간에 문제를 잡습니다. 방금 인덱스에 추가한 diff를 검사해서, 새 줄이 너무 길거나, 같은 원본 소스가 두 줄로 중복 색인되었거나, 예전 항목을 은퇴시키지 않고 새 이벤트 포인터만 추가했다면, 그 피드백을 **방금 쓴 바로 그 Claude 세션**으로 돌려보냅니다 — `PostToolUse` 훅의 `hookSpecificOutput.additionalContext` 필드를 통해서이며, `exit 2`는 아닙니다(이건 사람에게만 보이고 모델의 컨텍스트에는 도달하지 않습니다).

## 충돌 해결

두 메모리가 서로 다른 말을 할 때, 해결 순서는: 여러분이 그 자리에서 내린 명시적 지시(항상 최우선) > 원본 소스 파일 > 트리거 테이블 투영 > 인덱스 훅 라인 > 오래된 로그 스냅샷. 같은 계층끼리 충돌하면 더 최근 날짜가 이깁니다. 그래도 해결이 안 되면, 시스템은 임의로 절충하지 않고 사용자에게 물어봅니다.

## 지난 6주 동안 바뀐 것

3계층 구조 자체는 버텨냈습니다. 아래 중 두 가지는 첫 커밋 시점에 이미 있었고 README에 적지 않았을 뿐이며, 나머지는 새로 넣은 것입니다.

**아카이브 계층**(`_archive_index.md`, 7월부터). 끝난 프로젝트와 식은 라인은 삭제하지 않고 강등시킵니다: 인덱스의 그 줄만 이 파일로 옮기고, 원본 소스 파일은 그 자리에 둡니다. 강등이 성립하는 조건은 "`MEMORY.md`에서 사라진 것이 전부 아카이브 파일에 들어갔을 것"입니다. 이 검사가 없으면 강등과 삭제는 데이터상으로 구분되지 않습니다.

**프로젝트 도시에**(`projects/<이름>.md`, 8월 말). 인덱스는 장부가 되어 있었습니다. 인수인계, 점검, 결정이 건당 한 줄씩 끝없이 덧붙고, 링크의 38%가 날짜로 이름 붙은 로그 파일을 가리켰습니다. 이제 장기 프로젝트마다 자체 타임라인을 가진 문서를 하나씩 두고, 새 로그는 인덱스가 아니라 그 문서에 덧붙입니다. 프로젝트 다섯 개를 이렇게 정리하자 인덱스가 24,349자에서 20,782자로 줄었고, 링크는 하나도 잃지 않았습니다.

**인덱스 분할**(`_matrix_index.md`, 8월 말). 인덱스는 한 달에 두 번 상한에 부딪혔습니다(Claude Code는 24,400자에서 읽기를 멈춥니다). 한 프로젝트 묶음이 113개 포인터 줄 중 66줄, 문자 수의 57%를 차지하고 있어서 구획째 독립 인덱스 파일로 옮기고, 메인 인덱스에는 그것을 가리키는 한 줄만 남겼습니다. 한 번의 감소가 요점은 아닙니다. 이후 새로 생기는 줄의 절반가량이 상시 로드되는 파일 대신 분할된 쪽으로 들어갑니다.

**쓰기 경로가 사각지대였습니다.** 이 저장소의 hook은 `PostToolUse`의 `Write|Edit`에서 발동합니다. `Bash`를 거친 쓰기(python 스크립트, `sed`, 리다이렉트)에서는 백업도 git 커밋도 사이즈 게이트도 전혀 돌지 않았습니다. 하필 그게 게이트가 가장 봐야 할 일괄 편집입니다. 몇 주 동안 눈치채지 못했습니다. 해결책은 기억 파일 경로를 알아보는 `Bash` matcher를 더하고, 커밋되지 않고 남은 변경을 주워 담는 예약 작업을 두는 것입니다. hook을 가져다 쓴다면 이 교훈도 같이 가져가세요.

**용량은 바이트가 아니라 문자 수로 재야 합니다.** `wc -c`는 인덱스 용량을 한 번 이상 잘못 진단했습니다. 기록으로는 네 번입니다. 한중일 문자와 영어가 섞인 글은 문자당 대략 1.6~1.9바이트라서, 바이트로 재면 60~90% 높게 나오고 실제가 1.5만 자쯤일 때 24,400 임계값에 걸립니다. 사이즈 게이트의 모든 임계값은 `len(open(path, encoding='utf-8').read())`를 쓰며, 첫 커밋 이전부터 그랬습니다.

### 2계층의 비용

2계층은 비율을 지키지 못했습니다. 트리거 테이블은 전체 용량의 13%로, 첫 커밋 당시의 6%에서 두 배 넘게 늘었고 한 파일에 849,747자입니다.

퇴역한 항목은 원인이 아닙니다. 맨 아래 "보관 / 정리됨" 절은 약 1,600자, 스무 줄 남짓이고, 각 줄은 "그건 이미 끝났으니 지금은 X를 보라"고 답하는 북마크입니다. 여기서 퇴역이란 삭제가 아니라 북마크로 강등한다는 뜻입니다. 몇 달 뒤에도 사람은 옛날 코드네임을 치기 때문입니다.

원인은 살찐 카드입니다. 항목 733개, 중앙값 741자. 2,000자를 넘는 111개가 파일 전체의 49%를 차지하고, 가장 큰 것은 17,604자입니다. 테이블 자신의 규칙은 "현황 한 줄과 단단한 사실, 세부는 원본 소스로"입니다. 이 규칙은 7월에 한 번 손으로 적용해 파일을 107K에서 73K로 줄였지만, 두 달 만에 되돌아왔습니다. 스톡 게이트는 새 항목이 800자를 넘은 날 한 번 알려줍니다. 이미 살쪘고 계속 길어지는 항목은 아무것도 울리지 않습니다. 플로우 게이트는 이 파일을 보지도 않습니다. 차분을 뜨는 대상은 `MEMORY.md`뿐입니다.

트리거 단어의 조회 데이터는 아직 뽑지 않았지만 존재는 합니다. 테이블에 대한 grep은 전부 세션 기록에 남아 있고, 지난 한 달간 190개 세션에서 874번이었습니다. 뽑기 전까지는 하중을 받는 카드와 그냥 오래된 카드를 구별할 수 없습니다.

이 규모에서도 "먼저 grep, 그다음 읽기"는 작동합니다. 대신 무너지는 건 단어 선택입니다. 제가 자연스럽게 칠 만한 표현 14개로 찾아보니 5개가 빈손이었고, 모두 그날 새로 쓰였으면서 제가 실제로 쓰는 말이 아니라 시스템 이름으로 적힌 항목에 걸렸습니다.

(수치는 2026-09-16 실측입니다.)

## 설치

1. `hooks/memory_backup.sh`와 `hooks/memory_size_gate.py`를 `~/.claude/hooks/`에 복사하고, 각 파일 상단의 플레이스홀더 경로(백업 대상, 알림용 env 파일, 메모리 디렉토리)를 자신의 것으로 수정합니다.
2. 백업 훅을 `~/.claude/settings.json`에 연결합니다:

```json
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Write|Edit",
        "hooks": [
          {
            "type": "command",
            "command": "jq -r '.tool_input.file_path // empty' | /bin/bash $HOME/.claude/hooks/memory_backup.sh",
            "timeout": 120,
            "async": true
          }
        ]
      }
    ]
  }
}
```

3. 자신만의 메모리 디렉토리를 만들고(파일 구조는 `demo/` 참고) `MEMORY.md`에 한 줄짜리 훅으로 항목을 작성하기 시작하세요. 실제 세부 내용은 그 옆의 각 주제별 파일에 둡니다.
4. 백업/사이즈 게이트에 Telegram 알림을 연결하고 싶다면, `TG_TOKEN` / `TG_CHAT_ID`를 env 파일에 넣고 `TG_ENV`가 그 파일을 가리키게 하세요 — 이 파일은 절대 커밋하면 안 됩니다(`.gitignore`에 이미 포함되어 있습니다).

## `demo/`에는 무엇이 있나요

예상되는 형식을 보여주는 완전히 가상의 예제 파일들입니다(가상의 "위젯 출시" 프로젝트) — `MEMORY.md` 인덱스 항목, 트리거 테이블 발췌, 원본 소스 주제 파일 하나. 이 저장소에는 실제 프로젝트, 고객, 계정 정보가 전혀 없습니다. README에 나오는 수치(644만 자, 0.26%, 3계층 구조)는 제 실제 사용 데이터에서 가져온 것이지만, 여러분이 볼 수 있는 파일 내용은 전부 예시용 자리표시자입니다.
