# claude-memory-bookstore

[English](README.md) · [简体中文](README.zh-CN.md) · **繁體中文** · [한국어](README.ko.md) · [日本語](README.ja.md)

一套給 [Claude Code](https://claude.com/claude-code) 用的持久記憶系統,可以撐到數百個檔案、數百萬字元,但每次對話自動載入上下文的,永遠只有極小一部分。

我自己已經跑了好幾個月,橫跨數十個長期專案。上次檢查時:**存了 250 萬字元,每次對話自動讀進上下文的只有 0.8%。** 這不是 bug,這就是整個設計的目的。

**六週後重新量了一次:644 萬字元、921 個檔案,而自動載入的索引降到了 0.26%。** 庫大了 2.6 倍,常駐上下文的成本反而降到三分之一。這六週改了什麼寫在靠後的章節裡,包括變差的那個比例。

## 這套系統解決什麼問題

Claude Code 的對話上下文是有限的,但記憶庫沒有上限。如果你想讓 AI 助理「記住一切」,每次都把全部歷史餵給它,結果會適得其反:它會讀錯重點、漏掉關鍵資訊,速度比不用記憶系統還慢。

真正的解法不是檢索更多,而是預設載入得更少,並且教會系統「去哪查」,而不是「記住什麼」。

## 三層架構

```
第 1 層 — 索引(始終載入)         佔總體積 0.26%,載入頻率 100%
第 2 層 — 觸發詞與規則(按需)     佔總體積 13%,被 grep 命中時才載入
第 3 層 — 真實來源(按需)         佔總體積 87%,被開啟時才載入
```

**第 1 層 —— `MEMORY.md`。** 每條記憶只佔一行:「檔案存在 + 一句鉤子」。它不儲存知識本身,只儲存**去哪找知識**。這是唯一一個 Claude Code 會自動讀進每個新對話的檔案。

**第 2 層 —— 觸發詞表 + 規則。** 一張手動維護的反向索引,把「觸發詞」(你自然會想起來去搜尋的那些暗號/關鍵字)對應到真實來源檔案。這個檔案會長得很大(我自己那份超過 10 萬字元),所以紀律是:先 `grep`,再依行號讀取。整份讀完會被靜默截斷,後半部分會在你毫無察覺的情況下遺失。

**第 3 層 —— 真實來源。** 每個專案/主題一個檔案,每次交接一份日誌,每個重大拍板一份決策記錄。所有結論以這裡為準。上面兩層都只是它的投影——一旦和第 3 層有衝突,永遠第 3 層說了算。

## 讀取路徑:一個關鍵字如何找到知識

1. 你在任意對話裡打一個觸發詞——專案代號、事故名稱,或任何你自然會想到的說法。
2. Claude 去觸發詞表裡 grep 它(不是整份讀,見上面第 2 層)。
3. 拿到一個指標 + 一句話現況:`狀態 觸發詞A · 觸發詞B → 真實來源檔案 [硬事實]`。方括號裡只放 grep 命中當下就需要用到的東西:回滾指令、硬數字、結論。
4. 開啟真實來源檔案,繼續工作。索引裡快取的判斷不算數——只有真實來源檔案的結論才算數。

## 寫入路徑:三道自動關卡

**第 0 道關卡 —— 備份 + 版本層**(`hooks/memory_backup.sh`,在每次 `PostToolUse` 的 `Write|Edit` 觸發):把記憶目錄鏡像到備份位置,並在每次寫入時提交到 git。如果備份硬碟沒掛載,它會靜默失敗並只發一則去重後的告警,而不是無限重試——硬碟恢復後下一次寫入會自動補齊。

**第 1 道關卡 —— 存量關卡**(`hooks/memory_size_gate.py`):當索引體積超過閾值,或觸發詞表某一天漲得太多時,透過你自己接的通知管道提醒你。三條判據,每條每天最多觸發一次,不會變成你學會忽視的雜訊。

**第 2 道關卡 —— 流量關卡**(同一個程式裡新增的部分):光有存量關卡還不夠。對索引膨脹做過一次成分分解後發現,**新增行數 vs 舊行變肥的比例大約是 4~7:1**——也就是說,定期清理永遠只是治標,隔天症狀照樣復發。流量關卡改在寫入的那一刻就攔截問題:它檢查你剛剛往索引裡加的這段差異——如果新增行太長、同一個真實來源被兩行索引重複指向、或是加了新的事件指標卻沒有汰換舊的——就會把這條回饋發回**目前正在寫入的那個 Claude 對話**,走的是 `PostToolUse` hook 的 `hookSpecificOutput.additionalContext` 欄位,而不是 `exit 2`(後者只有人看得到,進不了模型的上下文)。

## 記憶衝突時,誰說了算

兩條記憶打架時,裁決順序是:你當場給出的明確指令(永遠最高)> 真實來源檔案 > 觸發詞表投影 > 索引鉤子行 > 舊的日誌快照。同層衝突按日期較新者勝。裁不出來的時候,系統會詢問你,而不是自己折衷猜一個答案。

## 這六週改了什麼

三層結構本身站住了。第一次提交之後加的東西:

**降層歸檔**(`_archive_index.md`)。做完的專案和冷掉的線不刪,只降層:索引裡那行挪進另一個檔案,真實來源檔案原地不動。刪掉會丟掉「這事我們試過」這個答案,而那恰恰是我查得最多的一種。

**分區索引。** 索引自己也會撞天花板。有一個專案在索引裡長到了 66 行,佔掉整份檔案的三分之二,而那攤事我並不是每天都碰。這 66 行被拆進 `_matrix_index.md`,主索引裡只留一行指過去。

**從「按事件記帳」改成「按專案歸檔」。** 索引一開始是流水帳:一件事一行,不停往後追加。改成按專案歸檔(一個專案一份檔案,新發生的事追加進檔案而不是追加進索引)之後,索引從 24,349 字元降到 20,760,沒丟任何東西。

**量體積只能用字元,不能用位元組。** `wc -c` 把索引體積誤診過三次我才發現。中日韓文字一個字元佔 3 位元組,所以位元組數會高報三倍。現在體積關卡裡所有閾值都走 `len(open(path, encoding='utf-8').read())`。

### 變差的部分

第 2 層沒守住比例。觸發詞表現在佔總體積 13%,比上面寫的 6% 漲了一倍多,單個檔案 849,747 字元。

流量關卡減緩了增長但沒有止住。它能抓「某一行太長」和「同一個真實來源被兩行索引」,但抓不住一行本來就該存在、而且每個月還在繼續往上長。真能治這個的關卡是「退掉沒人再敲的觸發詞」,這個關卡還不存在,因為我手上沒有哪些觸發詞真被命中過的資料。

在這個體積下「先 grep 再讀」的紀律仍然有效,所以這是成本問題不是正確性問題。

## 安裝

1. 把 `hooks/memory_backup.sh` 和 `hooks/memory_size_gate.py` 複製到 `~/.claude/hooks/`,並把每個檔案開頭的佔位路徑(備份目標、通知用的 env 檔案、記憶目錄)改成你自己的。
2. 在 `~/.claude/settings.json` 裡接上備份 hook:

```json
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Write|Edit",
        "hooks": [
          {
            "type": "command",
            "command": "jq -r '.tool_input.file_path // empty' | /bin/bash $HOME/.claude/hooks/memory_backup.sh",
            "timeout": 120,
            "async": true
          }
        ]
      }
    ]
  }
}
```

3. 建立你自己的記憶目錄(檔案排列參考 `demo/`),開始把 `MEMORY.md` 寫成一行一個鉤子,具體細節放進旁邊對應的 topic 檔案裡。
4. 如果想幫備份關卡/體積關卡接上 Telegram 告警,把 `TG_TOKEN` / `TG_CHAT_ID` 放進一個 env 檔案,讓 `TG_ENV` 指向它——這個檔案絕對不能提交進 git(已經寫在 `.gitignore` 裡)。

## `demo/` 目錄裡是什麼

一套完全虛構的範例檔案(一個假想的「widget 發布專案」),用來展示預期的檔案格式——`MEMORY.md` 索引條目、觸發詞表片段、一份真實來源 topic 檔案。這個儲存庫裡沒有任何一條是真實專案、客戶或帳號資訊;README 裡的數字(644 萬字元、0.26%、三層架構)來自我自己的真實使用情況,但你能瀏覽到的檔案內容全部是佔位符。
